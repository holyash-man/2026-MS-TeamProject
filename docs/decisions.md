# 결정 기록

진행 중 내린 결정과 그 판단 기준을 남긴다. 결정이 바뀌면 지우지 않고 아래에 새 항목을 추가한다.

## 판단 기준 (기본)

결정할 때 아래 순서로 따진다. 앞 기준이 갈리면 뒤 기준은 보조로만 쓴다.

1. **과제 요구사항 충족**: 과제 PDF의 기능·제출물 요구를 빠짐없이 만족하는가.
2. **채점 기여**: 기능 50 / 계산 정확성·테스트 20 / AI 로그 20 / 미적요소 10 중 어디에 얼마나 기여하는가.
3. **시연 안정성**: 시연 영상 촬영 때 깨지거나 재현이 어려울 위험이 없는가.
4. **비용과 일정**: 마감(12/15)과 B 파트 일정(~11/22 화면 연결) 안에 끝낼 수 있는가.
5. **A↔B 영향**: `Repositories.kt` 계약이나 A 파트 코드를 바꾸게 되는가. 바꾼다면 팀원과 먼저 합의한다.
6. **수업 내용과의 정합성**: 강의에서 다룬 방식(타입 세이프 내비게이션, Material3 테마, LazyColumn 등)과 맞는가.

## 함께 정하는 결정

아래에 해당하면 혼자 정하지 않고 팀원(또는 조정민-Claude 간)이 같이 판단한다.

- A↔B 계약(`Repositories.kt`, ViewModel 공개 상태) 변경
- 공용 파일(`build.gradle.kts`, `libs.versions.toml`, `DietNavHost.kt`) 변경
- 기능 범위를 늘리거나 줄이는 것
- 되돌리기 어려운 것(레포 이름, 브랜치 보호, 제출물 형식 등)

그 밖의 화면 구성·컴포넌트 분리·문구 같은 결정은 위 기준으로 바로 정하고 여기에 기록한다.

## D1 · 화면 작업은 "뼈대 PR"부터 (2026-11-16)

- 선택지: (a) 빈 파일·폴더만 만드는 구조 PR / (b) 화면 4개가 ViewModel에 연결되고 이동까지 되는 뼈대 PR
- 결정: **(b)**
- 근거: 프로젝트 전체 틀은 이미 PR #1에서 잡혔다. Kotlin 빈 파일은 정보가 적고(기준 2), ViewModel 연결을 먼저 해 두면 A↔B 계약 문제가 일찍 드러난다(기준 5). 팀 일정 "~11/22 화면 연결"과도 맞는다(기준 4).

## D2 · 내비게이션은 타입 세이프 라우트로 (2026-11-16)

- 선택지: (a) 지금의 문자열 route 유지 / (b) `@Serializable` 라우트 + `toRoute()`
- 결정: **(b)**
- 근거: 8주차 강의에서 다룬 방식이다(기준 6). 상세·수정 화면에 `mealId`를 넘길 때 타입 실수를 컴파일 단계에서 잡는다(기준 3). serialization 플러그인이 이미 있어 의존성 추가가 없다(기준 4). ViewModel은 `SavedStateHandle["mealId"]`로 읽으므로 라우트 프로퍼티 이름을 `mealId`로 두면 A 코드 변경이 없다(기준 5).
- 공용 파일 `DietNavHost.kt`를 고치므로 팀원에게 미리 공유한다.

## D3 · 사진 입력은 갤러리(Photo Picker)만 (2026-11-16)

- 선택지: (a) 갤러리만 / (b) 갤러리 + 카메라
- 결정: **(a)**, 시간이 남으면 카메라를 추가 기능으로 검토
- 근거: 과제 요구는 "음식 사진 입력"이라 갤러리로 충족된다(기준 1). Photo Picker는 저장소 권한이 필요 없고, 카메라는 권한 요청·촬영 파일 저장 처리가 추가된다(기준 4). 에뮬레이터 카메라는 가상 장면만 찍혀서 시연에서 얻는 이점이 작고, 갤러리에 음식 사진을 미리 넣어 두는 편이 영상이 더 깔끔하다(기준 3).

## D4 · 사진은 앱 내부 저장소로 복사해 저장 (2026-11-16, 팀원 확인 필요)

- 선택지: (a) Photo Picker가 준 URI만 저장 / (b) 앱 내부 저장소에 복사하고 그 경로를 저장
- 결정: **(b)** 로 제안
- 근거: Photo Picker URI는 접근 권한이 일시적이라, 앱을 다시 켰을 때나 원본을 지웠을 때 사진이 안 보일 수 있다. 시연 영상에서 목록 사진이 깨지는 것은 기능 점수에 바로 영향을 준다(기준 1, 3).
- 역할 제안: B는 Photo Picker로 받은 URI를 그대로 `MealInputViewModel.onPhotoChange()`에 넘긴다. 저장할 때 내부 저장소로 복사하고 DB에 복사본 경로를 넣는 것, 끼니 삭제 시 파일을 지우는 것은 A(데이터 계층)가 맡는다. 이렇게 하면 화면 쪽 코드는 (a)와 (b)에서 똑같다(기준 5).

## D5 · 작업 반영은 패치 파일 방식 (2026-11-16)

- 선택지: (a) Claude가 레포에 직접 push / (b) Claude가 커밋을 패치로 만들고 조정민이 적용·push
- 결정: **(b)**
- 근거: 레포에 Claude GitHub 앱이 설치되어 있지 않아 (a)는 레포 소유자의 앱 설치가 필요하다. (b)는 추가 설정 없이 바로 가능하고, 어차피 단계마다 로컬에서 실행 확인을 하므로 그때 패치를 적용하면 된다(기준 4). `main`에는 직접 push하지 않고 PR 머지는 실행 확인 뒤 사람이 한다.

## D6 · 시연 영상은 유튜브 "일부 공개" (2026-11-16)

- 선택지: 비공개 / 일부 공개 / 공개
- 결정: **일부 공개**
- 근거: "비공개"는 초대한 계정만 볼 수 있어 링크를 제출해도 교수님이 볼 수 없다(기준 1). "일부 공개"는 링크가 있는 사람만 볼 수 있다.

## D7 · 화면은 Screen(상태 연결)과 Content(그리기)로 나눈다 (2026-11-16)

- 선택지: (a) 화면 함수 안에서 바로 ViewModel 을 받아 그린다 / (b) `XxxScreen` 은 ViewModel 상태를 받아 넘기기만 하고, 실제 그리기는 상태와 콜백만 받는 `XxxContent` 가 한다
- 결정: **(b)**
- 근거: UI 테스트에 가짜 상태를 바로 넣을 수 있어, 기기에 저장된 기록에 따라 테스트 결과가 달라지지 않는다(기준 2, 3). 강의에서 다룬 상태 끌어올리기(state hoisting) 방식이다(기준 6). ViewModel 은 그대로 써서 A 코드 변경이 없다(기준 5).

## D8 · 검증 흐름: 여기서 빌드·테스트 → 로컬 에뮬레이터 최종 확인 (2026-11-16)

- 패치를 넘기기 전에 Claude 작업 환경에서 빌드, 단위 테스트, UI 테스트 컴파일을 돌린다.
- 이 환경에는 에뮬레이터가 없으므로, UI 테스트와 화면 흐름은 Robolectric(JVM에서 안드로이드 화면을 흉내 내는 도구)으로 **임시로** 한 번 돌려 본다. 이 설정은 공용 파일(`app/build.gradle.kts`)을 바꿔야 해서 커밋하지 않는다.
- 최종 확인과 시연 영상용 테스트 실행은 Android Studio + 에뮬레이터의 `connectedDebugAndroidTest` 로 한다(과제가 요구하는 Compose UI 테스트는 androidTest 쪽).
- 근거: 로컬에서 "실행해 보니 컴파일 에러"로 오가는 횟수를 줄인다(기준 4). 실제로 첫 실행에서 작은 화면일 때 목록 아래쪽 줄이 안 보여 실패하는 테스트를 미리 잡았다(기준 3).

## D9 · 커밋 단위와 커밋 전 검증 규칙 (2026-11-20)

- 계기: 커밋 여러 개를 한 번에 넘기는 것을 보고, 커밋마다 판단·검증이 충분했는지 점검하라는 요청(AI 로그 #13).
- 점검 결과: 커밋을 하나씩 따로 빌드해 보니 "화면 공용 컴포넌트" 커밋에 임시 화면(PlaceholderScreen) 삭제가 섞여 그 커밋만으로는 빌드가 깨졌다. 삭제를 그 파일을 실제로 대체하는 "화면 뼈대" 커밋으로 옮기고, 두 커밋이 각각 빌드되는 것을 확인했다. 최종 코드는 이전과 같다(push 전이라 기록을 고쳐 다시 적용).
- 규칙 (앞으로 모든 커밋):
  1. 커밋 하나 = 설명 한 줄로 말할 수 있는 변경 하나. 그 커밋만으로 빌드가 된다.
  2. 넘기기 전에 커밋마다 따로 컴파일하고, 마지막 커밋에서 단위 테스트 전체와 UI 테스트 컴파일을 돌린다.
  3. 커밋 안에서 내린 판단은 커밋 메시지 본문이나 이 문서에 근거를 남긴다. 말없이 정한 것을 두지 않는다.
  4. 기준(판단 기준 1~6)으로 바로 정할 수 있는 것은 정하고 기록만 한다. "함께 정하는 결정"에 해당하면 먼저 묻는다.

## D10 · 화면 뼈대에서 내린 세부 판단 (2026-11-20 정리)

D9 점검 때, 뼈대 커밋 안에서 기록 없이 정한 것들을 찾아 근거를 붙인다. 바꿀 필요가 생기면 디자인 단계에서 조정한다.

| 판단 | 근거 |
|---|---|
| 시작 화면은 목록 | 원래 코드와 같음. 앱을 켜면 기록부터 보는 것이 자연스럽고, 시연도 목록에서 시작한다(기준 3). |
| 새 기록 저장 → 그 끼니 상세로 이동, 입력 화면은 비움 | 저장 결과(음식별 영양·열량)를 바로 보여 줘 "입력 → 상세 표시" 요구를 한 흐름에서 확인할 수 있다(기준 1, 3). 다음 기록은 빈 칸에서 시작한다. |
| 수정 저장 → 상세로 돌아감, 상세·수정에서 하단 탭 숨김 | 수정 중 탭을 눌러 이탈하면 입력이 사라지는 혼란을 막는다(기준 3). |
| 삭제는 확인 창을 거친다 | 되돌릴 수 없는 동작이다. 시연 중 실수로 지우는 위험도 줄인다(기준 3). |
| 날짜는 오늘 이후 선택 불가, 시각은 제한 없음 | 식단 "기록"이라 미래 날짜는 의미가 없다. 오늘 안의 시각까지 막으면 자정 근처 입력이 번거로워져 날짜만 막는다. |
| 음식 검색 결과는 8개까지 | 음식이 100개라 짧은 검색어(예: "밥")에서 목록이 길어져 아래의 담은 음식·미리보기가 밀려난다. 8개면 한 화면에 들어온다. |
| 목록 날짜 머리글은 스크롤해도 위에 붙어 있음(stickyHeader) | "날짜별 열량·끼니 수" 요구를 스크롤 중에도 보여준다(기준 1). 실험 API지만 Compose 기본 제공이다. |
| 하단 탭 아이콘 설명은 비움 | 바로 아래 글자(label)가 같은 내용을 읽어 주므로 화면 읽기 기능이 두 번 읽지 않게 한다. 정보를 담은 아이콘(뒤로·수정·삭제·빼기)에는 설명을 넣었다. |
| 화면 문구는 Kotlin 코드 안에 직접 둠(strings.xml 미사용) | 한국어 단일 언어 앱이고, UI 테스트가 문구로 노드를 찾는다. 옮겨도 점수 기여가 작아 일정 우선(기준 4). 디자인 단계에서 다시 본다. |
